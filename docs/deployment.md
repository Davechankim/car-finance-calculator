# GitHub · Sites 배포 운영 절차

이 프로젝트는 GitHub를 변경 이력과 자동 검증의 기준으로 사용하고, Codex Sites를
운영 버전 저장·배포 시스템으로 사용한다. 두 저장소는 역할이 다르므로 GitHub에
푸시했다고 운영 사이트가 자동으로 바뀌지는 않는다.

현재 운영 주소는
`https://yechan-car-finance-2026.godwkd1030.chatgpt.site`이며 소유자 전용 비공개
접근으로 유지한다.

## 자동으로 수행되는 검증

모든 PR과 `main` 푸시에서 GitHub Actions가 다음 두 작업을 병렬 실행한다.

1. `Test, typecheck, and build`
   - 고정 잠금 파일로 의존성 설치
   - Vitest 단위 테스트
   - TypeScript 검사
   - 프로덕션 빌드
   - Sites 서버 엔트리와 호스팅 설정 일치 여부 확인
2. `Browser E2E`
   - Chromium 설치
   - 기본 결과, 키보드 탭 이동, 입력·자동 저장, 항목 추가·복제·삭제 검증
   - 실행 보고서를 14일간 Actions 아티팩트로 보관

정기 의존성 업데이트와 보안 수정은 Dependabot PR로 생성되며, 동일한 두 검증을
통과한 뒤 병합한다. major 업데이트는 다른 변경과 묶지 않고 별도로 검토한다.

## 정상 배포 순서

1. 기능 브랜치에서 변경하고 PR을 만든다.
2. 두 CI 작업이 모두 통과한 것을 확인한 뒤 `main`에 병합한다.
3. 로컬 `main`을 원격과 fast-forward로 동기화하고 작업 트리가 깨끗한지 확인한다.
4. 테스트용 Chromium이 없다면 한 번만 `npx playwright install chromium`을 실행한다.
5. `npm ci` 후 `npm run release:check`로 단위 테스트, 타입 검사, 프로덕션 빌드,
   Sites 산출물 검사, 브라우저 E2E를 한 번에 재검증한다.
6. Sites의 단기 쓰기 자격으로 정확한 `main` HEAD를 Sites 소스 저장소에 푸시한다.
   자격 정보는 원격 URL이나 Git 설정, 파일에 저장하지 않는다.
7. Sites 공식 패키징 도구로 같은 커밋에서 생성된 `dist/`를 묶고, 해당 커밋 SHA로
   새 버전을 저장한다.
8. 저장된 버전을 소유자 전용 방식으로 운영 배포하고 성공 상태가 될 때까지 확인한다.

배포 버전의 `commit_sha`는 반드시 GitHub `main`의 배포 대상 커밋과 같아야 한다.
빌드 후 소스가 바뀌었다면 기존 번들을 사용하지 않고 5단계부터 다시 실행한다.

## 접근 범위와 브랜치 보호

- Sites 접근 범위는 별도 요청 전까지 소유자 전용으로 유지한다.
- 공개 전환이나 사용자·그룹 공유는 운영 영향이 있으므로 명시적 승인 후 변경한다.
- GitHub 저장소가 비공개 GitHub Free인 동안 서버 측 `main` 보호 규칙은 사용할 수
  없다. 저장소를 공개하거나 GitHub Pro로 전환하면 다음을 적용한다.
  - PR 경유 필수
  - `Test, typecheck, and build`와 `Browser E2E` 성공 필수
  - 최신 `main` 반영 필수
  - 강제 푸시·브랜치 삭제 금지
  - 대화 해결 및 선형 히스토리 필수
  - 1인 저장소이므로 승인 리뷰 수는 0으로 유지

## 롤백

장애가 발생하면 새 소스 커밋을 급히 덮어쓰지 않는다.

1. Sites의 저장 버전 목록에서 마지막 정상 버전과 연결된 커밋을 확인한다.
2. 해당 저장 버전을 다시 운영 배포한다.
3. GitHub에는 원인 수정 PR을 별도로 만들고 전체 CI를 통과시킨다.
4. 수정 버전을 정상 배포 순서로 다시 저장·배포한다.

`.openai/hosting.json`에는 Sites 프로젝트 연결 정보와 선택적 D1/R2 논리 바인딩만
둔다. 토큰, 비밀번호, API 키 같은 런타임 값은 저장소에 커밋하지 않는다.
